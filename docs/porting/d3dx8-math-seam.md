# The D3DX 8 math seam

`d3dx8.lib` is a Windows static library, so every `D3DXMatrix*`/`D3DXVec*` call the engine makes is a
symbol nothing defines off Windows. `Core/Libraries/Source/WWVegas/WWMath/d3dx8math.cpp` is where
those definitions live — empty on Windows, where the real library supplies them, so the port cannot
introduce a duplicate symbol into the 13 Windows configurations — and
`scripts/native-port-shims/d3dx8math.h` is where they are declared for the native build. Five names
were already there for levels 1-3; this slice adds the rest of the set the renderer layer names.

The reason this seam has its own document and its own test is that it is **pure convention**, and the
convention is inverted between the two sides:

- D3DX puts the vector on the **left** of the matrix, `v' = v * M`. Translation is therefore in the
  fourth **row**, and `D3DXMatrixMultiply(out, A, B)` means "A then B" reading left to right.
- WWMath's `Matrix4x4` stores rows and multiplies a **column** vector on the right, `v' = M * v`.
  `To_Matrix4x4()` transposes a `_D3DMATRIX` on the way in; that transpose is part of its contract.

Neither the operand order nor the transpose is visible to a compiler or a linker. An implementation
with either reversed builds, links, and draws a subtly wrong picture — water reflections in the wrong
place, sorted geometry projected against the wrong matrix. So the deliverable of this slice is a
numerical assertion, not an object count.

## 2. What is implemented, and how the conventions land

In `d3dx8math.cpp`, off Windows only:

| Entry point | Route |
|---|---|
| `D3DXMatrixInverse` (`determinant` may be null) | `Matrix4x4::Inverse` on the converted matrix — inversion and transposition commute and a determinant is transpose-invariant, so the conversion survives it |
| `D3DXMatrixMultiply` | `Matrix4x4` multiply of the converted operands **in the opposite order**: `To_Matrix4x4(A) * To_Matrix4x4(B)` is `Aᵗ · Bᵗ = (B · A)ᵗ`, so `out = A · B` needs `converted_right * converted_left` |
| `D3DXMATRIX::operator*` | `D3DXMatrixMultiply(&out, this, &other)`, which is the order `sortingrenderer.cpp` relies on |
| `D3DXVec3Transform`, `D3DXVec4Transform`, `D3DXVec4Dot` | conversion plus the ordinary WWMath transform, i.e. a row vector on the left |
| `D3DXMatrixIdentity`, `D3DXMatrixTranspose`, `D3DXMatrixScaling`, `D3DXMatrixTranslation`, `D3DXMatrixRotationZ` | written straight into the D3DX layout — translation in the fourth row, `sin` above the diagonal. Routing a definition through WWMath would only add a transpose to undo |
| `D3DX_PI` | the header's own value |

`W3DWater.cpp` is the one engine file touched, by one include: it needs `ID3DXBuffer` and
`D3DXAssembleShader` as well as the matrix helpers, and only `d3dx8core.h` declares those. It has to
be the single source of the math declarations in that unit — the port's stand-in `d3dx8math.h`
*replaces* the vendored math header rather than complementing it, and a unit that reached both would
define `D3DXMATRIX` twice. The entry points are declared with C linkage in both, so it does not matter
which of the two a unit saw: both spell the same symbol and `d3dx8math.cpp` defines it once for
either. (`D3DXMatrixIdentity` is the exception D3DX itself makes — the vendored `d3dx8math.inl`
defines it inline, so `W3DWater.cpp` uses Microsoft's own definition and never reaches ours.)

## 3. `D3DXAssembleShader`/`ID3DXBuffer` are not behind a disabled `#if`

Worth stating plainly, because the cheap answer would have been to declare them unreachable and move
on. In `W3DWater.cpp` the assembly call sits under a runtime capability test, not a preprocessor one:

```
if (W3DShaderManager::getChipset() >= DC_GENERIC_PIXEL_SHADER_1_1)
    ...
    hr = D3DXAssembleShader(shader, strlen(shader), 0, nullptr, &compiledShader, nullptr);
```

So it is live code on any chipset that reports ps.1.1, and its symbol is genuinely unresolved off
Windows. `W3DProfilerFrameCapture.cpp` has a second assembly path and that one *is* behind
`#ifdef PROFILER_ENABLED`. Assembling ps/vs 1.1 assembly is a shader-translation problem (the spike's
16 shaders, `docs/porting/renderer-surface.md`), not a matrix-maths one, so it is reported here and
left to that slice rather than stubbed to something that returns success.

## 4. The assertion

`scripts/native-d3dx8math-test.py` compiles `WWMath/tests/d3dx8math_test.cpp` against
`d3dx8math.cpp` and `matrix4.cpp` with clang and runs it: **86 checks, 0 failures**. It follows the
standalone-clang-check pattern of `scripts/native-layout-test.py` and
`scripts/ci/check-font-metrics.py`, and runs in the `native-build` job of
`.github/workflows/native-port-ci.yml`. On Windows it refuses to run and says why: there the entry
points come from `d3dx8.lib`, and asserting against the real library is the Windows build's job.

Every matrix in it is asymmetric, so a stray transpose or a reversed product cannot pass by
coincidence. What it asserts:

- `M · M⁻¹` and `M⁻¹ · M` are the identity within `1e-4`, multiplied out by a reference loop written
  independently of the implementation (`sum += left.m[row][k] * right.m[k][column]`), and the
  determinant out-parameter is the known value for the test transform.
- A singular matrix returns null, and the output matrix still holds the sentinel it held before the
  call — D3DX does not write garbage on failure. Checked for a zero row and for a rank-deficient
  repeated row.
- A null `determinant` pointer is accepted.
- `D3DXMatrixMultiply(out, A, B)` equals the reference `A · B` — the D3DX order — and specifically
  **not** `B · A`, which is what forwarding straight to WWMath would produce. Same for
  `D3DXMATRIX::operator*`, and with `out` aliasing either operand.
- Scaling on the diagonal; translation in the fourth **row**; `D3DXMatrixRotationZ` with `+sin` at
  `m[0][1]`; transpose including in place; a full turn of `2·D3DX_PI` back to the identity; and
  `D3DX_PI` itself.
- Vector transforms are row-vector transforms: `out[column] = Σ value[row] · m[row][column]`, so a
  translated point picks the translation up out of the fourth row.

It was verified by mutation, not just by passing: reversing the converted operands in
`D3DXMatrixMultiply` and moving the translation into the fourth column makes **11 checks fail**,
including every product-order and every transform check. Both mutations compile and link cleanly,
which is the point of the test.

No pixels were rendered for this slice and none are claimed. It defines maths entry points; the
picture they feed is the renderer spike's evidence, and `check-spike-render.py` is untouched.

# The GDI font seam

`WW3D2/render2dsentence.cpp`'s `FontCharsClass` is the engine's only text rasteriser. It builds its
glyph cache with GDI: `CreateFont`, a memory DC, a 24bpp top-down `CreateDIBSection`, `ExtTextOutW`
into that surface, `GetTextExtentPoint32W` and `GetTextMetrics` for the numbers, and then copies one
byte per pixel out as the glyph's alpha. Off Windows none of those types existed, so the header chain
that mentions `HFONT` failed 18 translation units — the W3D GUI gadgets, `W3DGameFont.cpp`,
`W3DDisplayString*.cpp`, `W3DFunctionLexicon.cpp` — before any of them reached a real portability
problem.

This slice defines those GDI entry points off Windows, **under their own names**, the way
`platform_win32_file.cpp` defines `FindFirstFileA`. `render2dsentence.cpp` and every consumer is
unchanged: no `#ifdef`, no call-site rewrite, and the Windows build still calls the real GDI.

## 2. Where the code lives

| File | What it does |
|---|---|
| `WWLib/platform/platform_win32_gdi_font.cpp` | the seam: `CreateFontA`, `CreateCompatibleDC`, `DeleteDC`, `GetDC`, `ReleaseDC`, `CreateDIBSection`, `SelectObject`, `DeleteObject`, `SetBkColor`, `SetTextColor`, `GetTextMetricsA`, `GetTextExtentPoint32W`, `ExtTextOutW`, `MulDiv` |
| `scripts/native-port-shims/windows.h` | the declarations and the `wingdi.h` constants (`TEXTMETRIC`, `FW_*`, `*_PRECIS`, `ANTIALIASED_QUALITY`, `BI_RGB`, `ETO_OPAQUE`, …), plus the `CreateFont`/`GetTextMetrics` aliases the call sites spell |
| `WWLib/win.h` | includes `<windows.h>` off Windows when the shim supplies one, which is what makes `render2dsentence.h`'s `HFONT`/`HDC`/`HBITMAP` members declarable |
| `WWLib/platform/tests/gdi_font_metrics_dump.cpp` | the metrics dumper, built twice: against real GDI to record the reference, and against the seam to compare |
| `scripts/ci/check-font-metrics.py` | the gate (section 3) |
| `scripts/ci/record-gdi-font-metrics.sh` | re-records `scripts/ci/font-metrics-reference.json` |

One rasteriser for every non-Windows platform — stb_truetype, not CoreText on macOS and something
else on Linux. `docs/porting/decisions-resolved.md`'s rule is to match the Windows build as closely
as possible; there is no GDI to match off Windows, so what gets matched is GDI's *metrics*, and two
backends would mean two sets of advance widths to keep matching them.

## 3. What is gated, and against what

The acceptance criterion is not "text appears". Every WND screen's layout numbers were authored
against GDI's advance widths and line height, so a rasteriser that draws beautifully with different
advances moves every label — and nothing else in the build would notice.

`scripts/ci/check-font-metrics.py` builds `gdi_font_metrics_dump.cpp` against the seam, runs it on
the same font file the reference was recorded with (`WW_FONT_PATH` pins the lookup), and compares 14
font cases — 8/10/12/14/16/18/24 point, regular and bold, plus the condensed shape
`Create_GDI_Font()` uses for the "Generals" font — over every printable ASCII character:

- `tmHeight`, `tmAscent`, `tmDescent` and `tmOverhang` **exactly**. Line height is a layout input.
- each advance to within **1 pixel**, and the width the 95-character run sums to within **1%**.

Measured today: the exact fields match in all 14 cases, the worst advance difference is 1 pixel, and
it occurs for 7 glyph/size pairs out of 1330 (`space`, `,` and `.` at 8pt; `?` and `K` at 12pt, in
both the natural and the condensed shape). Those seven are GDI's advances being grid-fitted by the
font's own hinting instructions, which stb_truetype does not execute; the per-run bound is there so
that one-pixel differences cannot all lean the same way and walk a label's right edge off its widget.

**The reference is recorded, not live.** `scripts/ci/font-metrics-reference.json` is what *Wine's*
gdi32 reported inside the container `scripts/docker-build.sh` builds the Windows executables with,
which is the only Windows text stack this port can reach from CI; its `provenance` block says so in
the file. Retail Windows GDI may differ, so re-recording it on Windows — build the same dumper there
and run it with the same font file and face name — is the open item this slice leaves behind. The
font is DejaVu Sans, because that is what both the build container and the CI runner have, and both
sides of the comparison are pointed at the same file so a difference is a difference in the text
stack and not in the typeface.

The check runs in the `native-build` job of `.github/workflows/native-port-ci.yml`.

## 4. What the portable side does

- **A font is an em size in device pixels.** `Create_GDI_Font()` passes a negative `lfHeight`, which
  is GDI's "the em square is this many pixels"; a positive one is cell height and is matched against
  ascent + descent instead. `tmHeight`/`tmAscent`/`tmDescent` come from `hhea`, rounded at that size,
  and `tmInternalLeading` is the excess of the cell over the em, as GDI defines it.
- **`tmAveCharWidth` is OS/2's `xAvgCharWidth`**, not the advance of `'x'` — they are different
  numbers for most faces, and the difference matters because `lfWidth` is a request *about*
  `tmAveCharWidth`. stb_truetype does not surface the table, so the seam parses the four bytes out of
  the font directory itself.
- **A non-zero `lfWidth` condenses the face** the way GDI does it: the whole-pixel advance times
  `lfWidth / tmAveCharWidth`, **rounded up**. Rounding up is not a guess — it is what reproduces the
  recorded advances exactly for all 95 characters of the condensed cases, where rounding to nearest
  misses 11 of them. This is the "Generals" font, i.e. most of the game's UI text.
- **Advances are per-glyph, rounded, no kerning**, which is what `GetTextExtentPoint32W()` of a
  single character reports and what the layout code stores as the character's width.
- **`ExtTextOutW` draws `TA_TOP|TA_LEFT`** — `(x, y)` is the top left of the cell, the baseline is
  `y + tmAscent` — honours `ETO_OPAQUE` by painting the rectangle with the background colour first,
  and blends grey coverage between the background and text colours, which is what
  `ANTIALIASED_QUALITY` asks for and what the caller's "keep the top 4 bits as alpha" expects.
- **Face names map to files through a table**: Arial (which `Create_GDI_Font()` already rewrites
  "Generals" to), Times New Roman and Courier New, each preferring the real face and falling back to
  its *metric-compatible* substitute (Liberation Sans/Serif/Mono are designed to have exactly those
  advance widths), then to DejaVu. `Data/Fonts` in the game directory is searched first, so a shipped
  font wins over anything installed; `WW_FONT_PATH` overrides the search entirely.
- **No new dependency.** stb_truetype is in the stb checkout `cmake/stb.cmake` already pins at
  `5c205738c19` for `stb_image_write`; this slice links `core_wwlib` against that existing target and
  adds `stb-src` to the native build's include path.

## 5. Deliberately not implemented

Each of these is refused or ignored rather than half-done, and none of them is on the engine's font
path. `CreateDIBSection` of anything but a 24bpp `BI_RGB` section and `CreateFontA` of a face with no
font file at all both fail loudly through `WWPlatform::Win32::Report_Stub()` and return null, which
`Create_GDI_Font()` already treats as a failure.

- clipping regions and `ETO_CLIPPED`, transforms, and text alignment other than the default
- ClearType / sub-pixel output: coverage is grey
- kerning, and synthetic italic or emboldening — a bold face that is not installed falls back to the
  regular file, so its advances are the regular face's
- every GDI object other than a font and a DIB section; `SelectObject` refuses handles it did not
  create rather than dereferencing them
- `GetDC()` returns a single shared do-nothing screen DC, because the two callers only pass it to
  `CreateCompatibleDC()`/`CreateDIBSection()`, neither of which reads anything out of it

## 6. Still open

- **The reference is Wine's gdi32, not retail Windows GDI** (section 3). Re-recording it on Windows
  is the highest-value follow-up, and it is a script invocation, not new work.
- **Nothing has been run.** The seam compiles, and its metrics are gated, but `render2dsentence.cpp`
  cannot link until the renderer backend slice lands, so no glyph has been drawn by the *engine* off
  Windows. The pixels the rasteriser produces are unverified; only the numbers are.
- **The face table is a table.** A `.wnd` or `FontDefaults.ini` asking for a face outside Arial /
  Times New Roman / Courier New gets the sans-serif fallback, with no report. Enumerating installed
  faces (fontconfig, CoreText) is the alternative, and it would reintroduce the per-platform backend
  this slice deliberately does not have.
- **`tmMaxCharWidth` is the maximum over printable ASCII**, not over the whole face. Nothing in the
  engine reads it; it is in the metrics dump for completeness.
- **Bold is a separate file, or nothing.** GDI would synthesise emboldening for a face with no bold
  file; here the regular face is used, so bold text is not bolder — visible, but metric-neutral.
- **Wide characters are unchanged**, per the deferred decision: the seam takes `WCHAR` as the build
  already defines it and never converts, so `docs/porting/widechar-fallout.md` still owns that
  question.

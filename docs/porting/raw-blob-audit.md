# Raw-blob serialization audit

An enumeration of the places that read or write a structure to disk as a raw byte blob, and
whether each is now protected by a layout assertion. This is a survey, not a fix list — most of
these are safe once `bittype.h` is fixed-width, and the ones that are not are called out.

Search used (over `Core/`, `Generals/`, `GeneralsMD/`):

```bash
grep -rnIE '\b(fread|fwrite)\s*\('               --include='*.cpp' --include='*.h' Core Generals GeneralsMD   # 110 hits
grep -rnIE '(Read|Write)\s*\(\s*&[A-Za-z_]+.*sizeof' --include='*.cpp'                Core Generals GeneralsMD
grep -rnIE 'memcpy\s*\('                          --include='*.cpp'                    Core Generals GeneralsMD
```

## Covered by assertions in this change

| Site | Structures | Assertions |
| --- | --- | --- |
| `WWLib/chunkio.cpp` (all chunk/microchunk reads and writes) | `ChunkHeader`, `MicroChunkHeader` | `chunkio.h` |
| `WWLib/chunkio.cpp` (`Write`/`Read` of vectors and quaternions) | `IOVector2/3/4Struct`, `IOQuaternionStruct` | `iostruct.h` |
| `WW3D2/htree.cpp`, `hmdldef.cpp`, `hcanim.cpp`, `collect.cpp`, `distlod.cpp`, `agg_def.cpp`, `aabtree.cpp`, `meshdam.cpp`, `texture.cpp`, `soundrobj.cpp`, `w3d_dep.cpp`, `snappts.cpp` | 73 `.w3d` structures | `WW3D2/w3d_file_layout.h`, included from `w3d_file.h` |
| `WW3D2/sphereobj.cpp`, `ringobj.cpp` | `W3dSphereStruct`, `W3dRingStruct` (declared outside `w3d_file.h`) | `sphereobj.h`, `ringobj.h` |
| `WWLib/TARGA.cpp` | `TGAHeader`, `TGA2Footer`, `TGA2Extension` and friends | `TARGA.h` |

The Targa structures were **broken**, not merely at risk: `TGA2Footer::Extension`/`Developer` and
four `TGA2Extension` offsets were declared `long`, so on LP64 the footer grew from 26 to 34 bytes
and the extension area from its documented 495 bytes to 519. They are `int32_t` now, with the
sizes asserted (the 495-byte figure is stated in the Targa 2.0 spec and in the header's own
comment, which is a useful independent check that the asserted numbers are right).

## Safe by construction, not asserted

* `Win32BIGFileSystem.cpp` / `StdBIGFileSystem.cpp` read the `.big` directory field by field with
  explicit 4-byte reads into `UnsignedInt`, never as a struct. Nothing to assert.
* `GameEngine` serialization (`DataChunk.cpp`, `Recorder.cpp`, `XferSave/XferLoad.cpp`) writes
  scalars one at a time, and `Lib/BaseTypeCore.h` already defines `Int`/`UnsignedInt`/`Short`/…
  in terms of `<cstdint>`, so those widths do not move under LP64.

## Remaining unsafe sites

1. **`WideChar` string payloads.** `DataChunk.cpp:360` writes `len * sizeof(WideChar)` bytes and
   the matching reader reads the same; `Recorder.cpp` does the equivalent for replay headers.
   `sizeof(WideChar)` is 2 on Windows and 4 natively, so these files are not interchangeable
   across platforms. Not fixed here — see `docs/porting/widechar-fallout.md`. Save games and
   replays are out of scope for this port, but `.str`/`.csf` string loading is not, and it lands
   in the same place.
2. **`W3DWaterTracks.cpp:975-983`** writes `m_type` (an enum, implementation-defined width) into a
   `.wak` file, and reads it back the same way. Both ends are ours and the file is generated by
   the editor, so this is self-consistent per platform but not portable between them. Unasserted;
   the struct is never written whole, so there is no single layout to assert.
3. **Network packet structs** (`NetworkDefs.h`: `TransportMessageHeader`, `TransportMessage`,
   `CommandPacket`) are `#pragma pack(1)` blobs put on the wire, not on disk. They contain only
   fixed-width members today, but nothing enforces that. Out of scope for this change; worth the
   same treatment before native multiplayer is attempted.
4. **`verchk.cpp:94`** memcpys a `VS_FIXEDFILEINFO` out of a Win32 version resource. Windows-only
   code, no native equivalent yet.

## Not a serialization problem, but found on the way

`CRCEngine` accumulated into a `long` and walked its input in `sizeof(long)` strides, so on LP64 it
consumed 8 bytes per step instead of 4 and produced a different value for identical input. It is
`int32_t` throughout now. `CRC::_Table` and `CRC::Memory`/`String` were `unsigned long`; the
arithmetic happened to stay inside 32 bits, so the values were correct, but the types are
`uint32_t` now to make that explicit.
